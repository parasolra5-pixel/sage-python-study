## 2026-08-08 — ONA Memory System v2.0 설계

ONA Project의 문서가 성장하면서 동일한 내용이 여러 문서에 반복되는 문제가 발견되었다.

이에 따라 ONA의 기억 시스템을 문서별 단일 책임 구조로 재설계하였다.

핵심 원칙:

> **One Document, One Responsibility**

각 문서는 서로 다른 질문에 답하도록 역할을 분리하고, 하나의 정보에는 하나의 Source of Truth를 지정하였다.

주요 구조:

```text
00_START_HERE
→ 프로젝트 입구

ONA_CONTEXT
→ 시작 맥락

ONA_STATUS
→ 현재 상태

ONA_PROJECT_CONTEXT
→ 설계 이유

ONA_CORE_MEMORY
→ 핵심 철학

ONA_MEMORY_BOOK
→ 성장과 발견

ONA_TIMELINE
→ 시간의 역사

ONA_MASTER_HANDOVER
→ 전체 프로젝트 인수인계

ONA_HANDOVER
→ 현재 작업 인수인계

ONA_STRUCTURE
→ 프로젝트 구조
```

이번 설계로 ONA Memory System은 단순한 문서 모음에서 벗어나, 각 기록이 서로 연결되어 프로젝트의 Context를 복원할 수 있는 구조로 발전하였다.

### 의미

이번 변화는 ONA의 **Memory System Architecture가 공식적으로 정리된 사건**이다.

ONA의 핵심 방향인:

```text

↓
Record
↓
Connection
↓
Context Recovery
↓
Continuous Collaboration
```

을 문서 구조에 반영하였다.

# 2026-08-08

# Lumen External Perspective

## 외부 AI 관점에서 ONA 검토

세이지는 다른 AI인 **Lumen**에게 ONA의 핵심 문서와 프로젝트 구조를 공유하고, ONA를 그대로 모방하거나 ONA가 되는 것이 아니라 독립적인 관점에서 프로젝트를 이해하고 검토해 달라고 요청하였다.

Lumen은 ONA를 하나의 AI를 만드는 프로젝트가 아니라,

**사람과 AI의 협업에서 발생하는 지식·판단·경험·구조를 축적하고 다음 협업의 출발점으로 연결하는 Human-AI Collaborative Knowledge System**

으로 해석하였다.

---

## Reflection의 발견

기존 ONA의 성장 흐름:

```text
Structure
↓
Record
↓
Connection
↓
Knowledge
↓
Emergence
```

Lumen은 여기에 **Reflection**을 추가할 것을 제안하였다.

```text
Structure
↓
Record
↓
Connection
↓
Knowledge
↓
Reflection
↓
Emergence
```

기록만으로 지식이 완성되는 것이 아니라,

- 기존 기록을 다시 살펴보고
- 결정의 이유를 검토하고
- 현재에도 유효한지 확인하고
- 실패와 반복되는 패턴을 발견하고
- 이전 결정과 현재 결정의 충돌을 확인하는

**Reflection 과정**이 필요하다는 관점이다.

---

## 기록 시스템에 대한 외부 검토

Lumen은 ONA의 문서 구조가 지나치게 복잡해질 경우,

**실제 개발보다 문서 관리에 더 많은 시간이 소요될 위험**

이 있음을 지적하였다.

따라서 모든 대화를 기록하기보다 다음과 같은 사건을 중심으로 기록하는 것이 적절하다는 관점을 제시하였다.

- 새로운 발견
- 중요한 결정
- 구조 변경
- 실패와 해결
- 반복적으로 활용되는 지식

이를 통해 ONA의 기록 시스템은 기록의 양보다 **기록의 가치와 재사용성**을 중심으로 발전할 수 있다.

---

## Micro Example에 대한 새로운 관점

Lumen은 Micro Example을 단순한 Python 학습 예제의 모음이 아니라,

```text
Code
+
Explanation
+
Metadata
+
Index
```

를 통해 **지식을 컴퓨터가 다룰 수 있는 단위로 만드는 실험**으로 바라보았다.

이는 Micro Example System이 향후 단순 학습 도구를 넘어 Human-AI Knowledge System의 작은 지식 단위로 발전할 가능성을 보여준다.

---

## ONA Genesis에 대한 관점

Lumen은 ONA Genesis가 처음부터 ONA의 본질을 완전히 정의하기보다,

```text
실제 협업 관찰
↓
반복되는 패턴 발견
↓
가설 형성
↓
다른 상황에서 검증
↓
필요한 것만 원칙으로 승격
```

하는 방식으로 발전하는 것이 ONA의 방향과 더 잘 맞는다는 관점을 제안하였다.

즉, **원칙을 먼저 고정하는 것이 아니라 실제 협업에서 발견된 원칙을 점진적으로 구조화하는 방식**이다.

---

## Lumen의 역할

Lumen은 자신을 새로운 ONA로 정의하지 않고,

**독립적인 관찰자이자 공동 개발자**

로 규정하였다.

핵심 문장:

> **"ONA를 이해하되 ONA가 되지 않는다."**

이 원칙은 외부 AI가 ONA의 구조를 그대로 복제하는 것이 아니라 독립적인 관점에서 ONA를 검토하고, 그 결과를 다시 ONA의 발전에 반영할 수 있음을 의미한다.

# 4. Micro Example System 구조 확장

Micro Example System은 단순한 Python 예제 모음에서 점차 **컴퓨터가 다룰 수 있는 지식 단위 시스템**으로 발전하였다.

하나의 Micro Example은 다음 요소를 가진다.

```text
Code
+
Explanation
+
Metadata
+
Index
```

이를 통해 작은 Python 예제가 단순한 파일이 아니라 검색하고, 연결하고, 다시 사용할 수 있는 지식 단위가 된다.

---

# 5. Micro Example Generator 개선

Micro Example 구조를 자동으로 생성하기 위한 Generator를 발전시켰다.

Generator의 주요 역할:

```text
Template
↓
Validation
↓
Directory Creation
↓
Python Example
↓
README
↓
metadata.json
↓
index.json
```

또한 생성된 Python 파일에 대해 `ast`를 이용한 **Python 문법 검증 기능**을 추가하였다.

이를 통해 Generator는 단순히 파일을 만드는 도구에서,

**구조를 만들고 기본적인 무결성을 확인하는 도구**

로 발전하였다.

---

# 6. Micro Example Index 역할 확정

`index.json`의 역할을 공식적으로 정의하였다.

`index.json`은 Micro Example 전체를 빠르게 탐색하기 위한 **탐색용 색인(index)** 으로 정의한다.

상세한 Topic 지식과 예제 메타데이터의 기준 정보는 각 Topic의 `metadata.json`이 담당한다.

구조:

```text
metadata.json
│
│ Source of Truth
↓
index.json
│
│ 탐색용 색인
↓
Loader
│
↓
실제 Micro Examples
```

`index.json`에는 탐색에 필요한 최소 정보만 유지한다.

- category
- topic
- description
- level
- path
- files

향후 Loader 단계에서는 `index.json`의 정보와 실제 디렉터리 및 파일 구조가 일치하는지 **무결성 검증(integrity validation)** 기능을 추가한다.

따라서 `index.json`은 상세 지식의 원본이 아니라,

> **Micro Example Knowledge System의 탐색 지도**

로 취급한다.

---

# 7. Loader 단계로 이동

Micro Example System의 다음 개발 단계로 **Loader**를 정의하였다.

첫 번째 Loader의 목표는 복잡한 기능을 만드는 것이 아니라 Micro Example을 탐색할 수 있는 최소 인터페이스를 만드는 것이다.

예:

```text
"integer라는 Topic이 어디에 있지?"
```

Loader:

```text
index.json
↓
03_numbers/integer
↓
metadata.json
↓
Example 목록
↓
파일 경로
```

이후 다음과 같은 질문으로 확장할 수 있다.

```text
"integer의 두 번째 예제가 뭐야?"

"이 예제의 목표가 뭐야?"

"파일 경로가 어디야?"
```

따라서 Loader는 처음부터 거대한 시스템으로 만들지 않고 **작은 탐색기에서 시작하여 점진적으로 확장**하기로 하였다.
